# 프레임워크 신뢰도 개선: 작업 의도와 인수기준

상태: 사용자 승인 완료. 작업 1~5 구현 기준 문서.

## 1. 목적과 기준

- 목적: 백테스트 결과의 신뢰도를 확보하고 사용자 전략의 실거래 도입을 준비한다.
- 사용 이력: 사용자는 f11edbe 기반 실거래 경험이 있으나, 중단·전략 수정·재배포 이후 문제가 발생하여 장기간 중단했다. 당시 장애의 원인은 미확인이며 특정 원인으로 단정하지 않는다.
- 구현 기준: origin/main의 737fbc93560c441bf51aea53d6b911968cf70b3a. 현재 작업 폴더의 과거 기능 브랜치를 구현 기준으로 사용하지 않는다.
- 전달: 아래 작업 1~5를 순서대로 작업별 PR로 제공한다. 필요한 의존성은 명시하고 자동 병합하지 않는다.
- 검증: 네트워크 없는 자동 테스트와 테스트넷 수동 점검 절차까지. 실제 계정 주문·배포는 이번 범위가 아니다.
- 기존 전략은 최소 수정만 허용하며, 공개 동작 변경에는 이유와 전환 예제를 제공한다.

## 2. 책임과 지원 범위

프레임워크는 실행·체결·회계·데이터 가시성·거래소 연결·상태 복구를 담당한다. 신호, 지표 계산 방법, 진입·청산 판단, 기존 주문 변경 판단은 사용자 전략이 담당한다. 로컬 사용자 전략은 별도 지시 없이 수정하거나 커밋하지 않는다. 검증에는 저장소 소유의 작은 테스트 전략을 사용한다.

- 실행 설정의 대상 종목은 해당 봇 전용이다. 대상 종목의 모든 기존 주문·포지션을 인계한다. 다른 종목의 주문은 관리하지 않는다.
- 단방향 모드만 지원한다. 헤지 모드는 거래소 변경 요청 전에 오류로 거부하며 자동 전환하지 않는다.
- 중복 방지·복구 보장은 프레임워크 주문 API를 사용하는 경로에 적용한다. SDK 직접 호출은 허용하지만 보장 밖이다.
- 정상 종료·재배포는 거래소 주문을 취소하거나 포지션을 청산하지 않는다.
- 비용·슬리피지·펀딩·청산 모델 확장은 이번 1~5번 범위 밖이다. 백테스트 기본 비용 0 가정은 명시한다.
- 같은 로컬 복구 기록 경로의 중복 실행은 차단한다. 서로 다른 경로나 서버 간 분산 잠금은 지원하지 않는다.

## 3. 작업별 의도와 AC

### 작업 1 — 입력 검증

의도: 잘못된 설정이 주문량·증거금·평가 범위 계산에 들어가기 전에 명확한 오류로 차단한다.

- AC-1.1: 레버리지는 bool을 제외한 양의 정수만 허용한다. 소수, NaN, 무한대, 0, 음수는 거부한다.
- AC-1.2: 백테스트 초기 잔고는 유한한 양수, 비중은 유한한 0 초과 1 이하, 워밍업은 bool을 제외한 0 이상의 정수만 허용한다.
- AC-1.3: 시간대 등 기존 검증을 유지하고 오류에 문제 필드를 표시한다. 정상 설정의 계산 결과와 기존 위치 인자 순서를 유지한다.
- AC-1.4: CLI 설정과 공개 설정 객체 경로 모두 같은 조건을 만족한다. 유효하지 않은 설정은 주문 전송 전에 실패한다.
- 검증: 비정상 값 매개변수 테스트, 경계값, 정상 주문량·증거금 회귀 테스트.

### 작업 2 — 품질 기준과 CI

의도: 개발 환경의 전역 도구 설정에 의존하지 않는 품질 기준을 만들고 후속 변경의 회귀를 차단한다.

- AC-2.1: Ruff와 mypy의 검사 대상·규칙·Python 기준을 저장소에 명시한다. CI와 로컬 실행 명령이 같다.
- AC-2.2: Python 3.12·3.13에서 패키지 설치, pip check, 전체 테스트를 통과한다. 품질 검사도 CI에서 수행한다.
- AC-2.3: 기존 린트·타입 오류를 해결한다. 프로젝트 전체 무시나 무분별한 Any로 통과시키지 않는다. SDK의 타입 정보 부재는 외부 모듈에 한정해 설명한다.
- AC-2.4: 이 PR은 서식·타입·CI 기준을 다루며 주문·체결·복구 정책을 변경하지 않는다.
- 검증: 명시적 저장소 설정으로 품질 검사, 전체 테스트, CI 결과.

### 작업 3 — 백테스트 시간 규칙

의도: 판단 시점 이후의 정보가 주문 결정에 들어가거나, 봉 마감 판단으로 과거 체결을 취소하지 못하게 한다.

- AC-3.1: 시장가 기본값은 다음 봉 시가다. 기존 종가 체결은 명시적으로 선택할 수 있다. README와 전환 예제에 기본값 변경을 설명한다.
- AC-3.2: 이전 시점에 접수한 주문의 만료·체결·회계를 해당 봉 규칙에 따라 처리한 뒤, 마감된 데이터를 제공해 전략을 호출한다. 새 비시장가 주문은 생성 봉에서 체결하지 않는다.
- AC-3.3: 전략에 제공하는 모든 종목·시간봉 데이터는 판단 시점까지 마감된 봉만 포함한다. 전체 원본은 엔진 내부에 보관하고 전략에 노출하지 않는다.
- AC-3.4: 같은 판단 시각의 기존 주문 처리를 모든 대상 종목에 먼저 반영한 후 전략 호출을 시작한다. 공유 잔고의 신규 주문 우선순위는 고정된 종목 순서로 재현된다.
- AC-3.5: 같은 봉에서 손절·익절이 모두 가능하면 손절 우선 규칙을 유지한다. OHLC의 봉 내부 순서 한계는 문서화한다.
- AC-3.6: 평가 종료 시 잔여 포지션은 마지막 평가 종가로 강제 청산하고 거래 결과에 종료 청산 사유를 표시한다. 마지막 봉의 다음 시가 주문은 미체결로 정리하고 예약 증거금을 해제한다.
- AC-3.7: 전략 예외는 백테스트 실패로 전달하며 정상 완료 결과를 반환하지 않는다.
- AC-3.8: 기존 콜백 형태는 가능한 한 유지하며, 현재 인덱스가 가시 데이터의 마지막 봉을 가리키도록 한다. 전체 데이터 사전 접근에 의존한 전략의 수정 예제를 제공한다.
- 검증: 같은 봉 취소로 과거 체결을 지우는 사례, 다음 시가 갭, 5분·1시간봉 가시성, 다른 종목 미래 정보, 다중 종목 공유 잔고, 마지막 봉 청산·미체결, 전략 예외, 반복 실행 결과 일치.

### 작업 4 — 거래소 어댑터와 공통 주문 경로

의도: SDK 변경을 도메인에서 분리하고, 공통 주문 API의 요청·응답·실패를 네트워크 없이 검증할 수 있게 한다.

- AC-4.1: 실행기가 거래소 어댑터를 주입받는다. 주입 경로에서 전역 client()를 우회 호출하지 않는다. 기본 생성 경로의 사용 편의는 유지한다.
- AC-4.2: 일반 주문과 조건부 주문의 전송·조회·취소, 주문 식별자, 잔고·포지션·계정 모드 조회, 과거 봉 조회, 스트림 구독을 명확한 어댑터 경계로 둔다.
- AC-4.3: SDK 객체의 변환은 어댑터 경계에서 수행한다. 도메인 테스트는 SDK 연결 없이 실행한다.
- AC-4.4: 공통 주문 API가 확정 거부와 결과 불명확 상태를 구별한다. 불명확한 결과를 단순한 주문 실패나 재전송 가능 신호로 반환하지 않는다.
- AC-4.5: 기존 공통 주문 헬퍼의 보장 여부를 문서에 열거하고, 관리 대상 헬퍼는 같은 주문 경로를 사용하게 한다. SDK 직접 호출을 공통 API로 옮기는 예제를 제공한다.
- 검증: SDK 7.1.1에 맞춘 일반·조건부 주문 변환 계약 테스트, 조회·취소 오류, 가짜 어댑터만으로 전략 실행.

### 작업 5 — 실거래 수명주기와 복구

의도: 시작·중단·재배포·연결 단절·불명확한 주문 결과에서 거래소 상태를 존중하며 중복 주문 없이 운영을 이어간다.

- AC-5.1: 시작 전에 실행 잠금과 계정 모드를 확인한다. 헤지 모드이면 주문·레버리지 변경 전에 거부한다.
- AC-5.2: 기존 잔고·주문·포지션·지표 데이터를 동기화한 뒤 전략을 활성화한다. 기존 주문은 자동 취소·재생성하지 않는다.
- AC-5.3: 기존 포지션의 거래소 레버리지를 유지한다. 해당 포지션의 추가 진입과 회계도 그 값을 사용한다. 완전 청산 후 다음 신규 진입 전에 새 설정을 적용한다. 레버리지 변경 성공 전 신규 주문은 보내지 않는다.
- AC-5.4: 연결 단절 감지 시 전략의 주문 실행을 보류한다. 복구 재시도는 간격을 늘리되 상한을 두고 계속한다. 상태 동기화가 성공해야 자동 재개한다.
- AC-5.5: 누락된 마감 봉을 보충해 지표를 복원하되 과거 봉에 대해 거래 콜백을 재실행하지 않는다. 동기화 이후 새롭게 마감된 봉부터 판단한다.
- AC-5.6: 중복·순서가 뒤바뀐 이벤트로 주문 상태가 되돌아가거나 부분 체결 손익이 두 번 누적되지 않는다. 동기화 중 도착한 이벤트와 조회 상태를 일관되게 반영한다.
- AC-5.7: 전략 예외는 해당 실행기의 추가 전략 호출·신규 주문을 중지하고 보고한다. 연결 복구가 전략 오류 중지 상태를 자동 해제하지 않는다. 기존 거래소 주문·포지션은 유지한다.
- AC-5.8: 정상 종료 시 새 작업을 받지 않고 진행 중 작업을 정리한다. 연결과 로컬 잠금을 해제하며 거래소 주문·포지션을 유지한다. 동일 실행기를 두 번 닫아도 안전하다.
- AC-5.9: 주문 식별자·최소 요청 정보·처리 상태를 전송 전에 로컬에 내구성 있게 저장한다. API 키·시크릿은 기록하지 않는다.
- AC-5.10: 응답 유실 시 식별자로 접수 여부를 확인한다. 확인 전 해당 종목 추가 주문을 보류하고 예약 증거금을 임의 반환하지 않는다. 접수 여부가 불명확한 주문을 자동 재전송하지 않는다.
- AC-5.11: 비정상 종료 후 미확정 기록을 조회·복원한다. 저장 경로가 없거나 쓰기에 실패하면 관리 대상 주문을 전송하지 않는다. 다른 계정의 기록을 조용히 재사용하지 않는다.
- AC-5.12: 같은 기록 경로로 두 번째 프로세스가 시작하면 거래소 변경 전에 차단한다. 비정상 종료 후에는 운영체제 잠금 해제로 재시작 가능해야 한다.
- AC-5.13: 로그와 설정된 알림 경로에 중단·복구·전략 오류·주문 불확실 상태를 알린다. 반복 재시도로 동일 알림을 무제한 발생시키지 않는다.
- 검증: 기존 주문·포지션 인계, 레버리지 전환, 부분 체결 중 단절, 중복 이벤트, 조회 중 이벤트, 반복 재접속, 누락 봉, 전략 예외, 정상·비정상 종료, 주문 접수 후 응답 유실, 전송 전 기록 실패, 프로세스 잠금.

## 4. 구현 기본안과 경계

다음은 인터뷰의 정책을 구현하기 위한 기본안이며 사용자 전략 정책을 추가하지 않는다.

- 로컬 저장은 Python 표준 SQLite와 프로세스 잠금으로 구성한다. 데이터 경로를 명시적으로 설정할 수 있게 하고 로그에 실제 경로를 표시한다.
- 복구 재시도는 1초부터 지수 증가, 최대 60초, 지터를 적용한다. 테스트에는 시계·대기 함수를 주입한다. 성공 시 지연을 초기화한다.
- 주문 불확실 상태는 기존 bool 성공/실패 계약과 구별되는 공개 예외로 전달한다. 프레임워크 실행기는 이를 포착해 해당 종목을 보류하며, 사용자 코드에 재전송을 유도하지 않는다.
- 주문 접수 거부가 확정되면 실패와 증거금 반환을 처리한다. 조회의 단순 미발견은 즉시 미접수 확정으로 간주하지 않는다.
- 기존 미체결 진입 주문이 남은 상태에서 레버리지를 전환하면 그 주문에도 영향을 줄 수 있다. 자동 취소하지 않고 기존 진입 주문이 해소된 뒤 새 레버리지의 신규 진입을 허용한다. 이 보류 이유를 보고한다.
- 주문 생성 시점보다 늦게 봉 데이터가 도착하더라도 이미 접수된 주문의 과거 체결을 전략 취소로 되돌리지 않는다.
- 자동 테스트의 성공은 실제 거래소 운영 검증 완료를 의미하지 않는다. 테스트넷 문서는 시작·인계·단절·재시작·종료·응답 유실 점검과 기대 결과를 포함한다.

## 5. 전달과 추적

1. 이 문서의 검토 후 작업별 구현 계획에 파일·인터페이스·테스트 명령을 구체화한다.
2. 작업 1 → 2 → 3 → 4 → 5 순서로 구현한다. 각 PR에 관련 AC ID, 검증 결과, 공개 동작 변경, 의존 PR을 기재한다.
3. 앞선 PR이 미병합이면 후속 PR의 기준 브랜치를 명시한 의존 PR로 제출한다. 자동 병합하지 않는다.
4. 각 AC를 테스트나 문서 검증 결과에 연결한다. 미충족 AC가 있으면 해당 작업을 완료로 보고하지 않는다.
5. 사용자 전략, API 키, 계좌 데이터, 로컬 복구 DB를 커밋하지 않는다.
